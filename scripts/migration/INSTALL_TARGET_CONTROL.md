# Tencent inert control installer

`install_target_control.py` is a local root installer for the fixed
`20261016` migration. Running it without arguments only prints an offline
description; it does not read stdin or perform host operations. The separate
`--install-inert` mode prepares a stopped application and its control plane.
It has no remote driver.

## Effects and boundaries

The installer verifies reviewed program bytes, creates one persistent shared
owner, invokes the reviewed `prepare_live_app.py` preparation function, and
adopts the actual inert application, standby PostgreSQL and standby Redis
identities into the target RPC configuration. It installs root-private
programs, configuration, bearer token and an epoch-zero RPC ledger. It then
appends one restricted root public key and enables only the target recovery
timer.

It never starts the application; starts, stops, or restarts PostgreSQL or
Redis; promotes a database; changes an application endpoint, DNS, ingress,
Ubuntu authorization, or global SSH configuration. Application creation and
the root control installation are local mutations. The timer can recover
accepted RPC intents later; with a fresh empty ledger it performs no business
effects.

The forced key line is generated by the installer, with no caller-supplied
options, path, command or comment:

```text
from="13.231.143.136",restrict,command="/usr/bin/python3 -I /usr/local/libexec/sub2api-migration-20261016/target_rpc.py serve" ssh-ed25519 <approved-blob> sub2api-migration-rpc-20261016
```

The key's private half stays on AWS. The installer never accepts or prints it.

## Required inputs

Staging has to be complete before bootstrap:

- `/home/ubuntu/sub2api-migration-20261016/control-staging/` contains the exact
  reviewed `install_target_control.py`, `prepare_live_app.py` and
  `target_rpc.py`, each mode `0600`.
- The reviewed preparer's source runtime, initial manifest and initial
  application files remain at its fixed staging paths. Its `load_inputs()`
  verifies their approved hashes and ownership.
- `/var/lib/sub2api-migration-20261016/postgres-authority/state.json` is the
  root-owned PostgreSQL authority record in `standby-role-aware-ready`,
  `STANDBY` mode with no promotion intent.
- `/home/ubuntu/sub2api-migration-20261016/redis-standby/ownership.json` is the
  exact approved mode-`0600` Redis ownership record.
- Staging ancestor directories are ordinary directories owned by root or
  UID `1000`, without group or other write permission. Symlinks and multiply
  linked staged files are refused. Installed files and all installed ancestor
  directories have to be root owned; private scopes have mode `0700`.
- Existing root SSH policy must already permit forced public-key access.
  Existing `/root/.ssh`, when present, must be root-owned mode `0700`, and
  `authorized_keys` must be root-owned mode `0600`.

An executing installer must first be bootstrapped to
`/usr/local/libexec/sub2api-migration-20261016/install_target_control.py` as
root-owned mode `0700`, under trusted root-owned directories. The bootstrap
operator must verify the approved exact byte hash before installing or
executing that file. Do not run a mutable Ubuntu staging script as root.
The installer additionally refuses any execution path or self hash other than
the reviewed fixed root path and approved bytes.

One bounded JSON approval object is supplied through root-controlled stdin:

```json
{
  "v": 1,
  "run": "20261016",
  "programs": {
    "install_target_control.py": "<exact-byte-sha256>",
    "prepare_live_app.py": "<exact-byte-sha256>",
    "target_rpc.py": "<exact-byte-sha256>"
  },
  "source_runtime_sha256": "5570f29f0954706128798f2d4575be4302a0508739d2e21c39e364c4d1dc16fd",
  "initial_manifest_sha256": "<exact-byte-sha256>",
  "redis_ownership_sha256": "<exact-byte-sha256>",
  "public_key": {
    "algorithm": "ssh-ed25519",
    "base64": "<canonical-ed25519-public-key-blob>",
    "sha256": "<sha256-of-decoded-ssh-wire-blob>"
  }
}
```

The public key hash is the SHA-256 of the decoded SSH wire blob, not the
public-key text or OpenSSH's formatted fingerprint. Only a canonical
`ssh-ed25519` wire encoding containing exactly one 32-byte key is accepted.
Metadata cannot supply a host, shell command, file path, service name or owner.
Unknown fields, duplicate JSON keys, trailing JSON, nonfinite values and
oversized input are refused. Input has a three-second deadline.

After the reviewed root bootstrap, the local entry point is:

```sh
/usr/bin/python3 -I /usr/local/libexec/sub2api-migration-20261016/install_target_control.py --install-inert
```

The caller provides the approved metadata on stdin and must retain the JSON
result. This document does not execute the entry point or grant additional
production authority.

## Adoption and SSH checks

The shared owner is persisted before application creation. RPC configuration
is derived from actual container IDs, image IDs, configuration hashes and
ordered RootFS DiffIDs. Existing PostgreSQL and Redis owner identities remain
separate from the shared application/RPC owner. Fixed PostgreSQL and Redis
image configuration digests are enforced, including Docker/containerd manifest
resolution when the image ID is a manifest or index digest.

The reviewed RPC backend performs its label, volume, mount, restart-policy,
PostgreSQL system-identifier, timeline and recovery checks. Redis must be a
connected replica using the loopback source channel, with sync complete and
no failover in progress. The current source Redis run ID must match the
approved ownership record; the current source and target replication IDs must
match. Redis may legitimately have created a new replication ID when the
replication backlog was first created, so the original ownership record's
replication ID is not treated as the current source ID.

The installer inspects `/usr/sbin/sshd -T -C` for root traffic from the fixed
AWS IP and the actual local address, once before host preparation and again
before writing the root key. It requires compatible `PermitRootLogin`,
`PubkeyAuthentication`, `AuthenticationMethods` and `AuthorizedKeysFile`
settings. It does not edit or reload `sshd`.
Only these four singleton fields are parsed; duplicate occurrences of them
are refused. Repeated unrelated multivalue directives such as `HostKey`,
`ListenAddress` and `AcceptEnv` do not cause a refusal.

Unrelated root authorization bytes are preserved. An exact managed entry is
idempotent. A changed or duplicate managed tag, or another root authorization
for the same public key, causes refusal. The authorized-keys write checks for
concurrent administrator edits before replacing the file.

Policy inspection is not an authentication proof. The parent migration
orchestrator must independently verify the restricted AWS-to-Tencent RPC
connection using the reviewed source-held key and pinned host identity before
accepting any migration intent.

## Persistent state and recovery

The installer state is stored under
`/var/lib/sub2api-migration-20261016/control-install/`. A retry must retain
the same machine, shared owner and exact approval metadata. Configuration and
installed code are create-or-match, so changed reviewed bytes require a
separate reviewed upgrade procedure rather than an overwrite.

An existing RPC ledger is accepted only if its complete schema still matches
the initial epoch-zero, empty-operation, AWS-authority state. A noninitial
ledger is never reset. If another operation changes the ledger during
preparation, the final create-or-match write refuses to overwrite it. Once
any migration intent is accepted, stop using this inert installer and recover
through the durable runner and target RPC.

Checkpoints precede application creation, key installation and guard enablement.
Lost write or timer-enable responses leave owned resources and checkpoints
in place. Retrying with unchanged reviewed input reconciles an installation
that remains inert. Do not delete owner state, recreate a container, reset an
RPC ledger, or restart an old primary to clear an uncertain result.

The installed guard uses exactly `target_rpc.py guard-reconcile`. The installer
checks loaded unit fragment paths and rejects all drop-ins before enabling
the timer, then verifies that the timer is active and enabled without a
pending job. It does not enable a business service.

Successful output includes the shared owner, machine and public-key hashes,
adopted resource IDs and RPC configuration hash. It explicitly reports false
for application start, data-service restart, promotion and DNS/entry change.
No bearer token, database credentials or process stderr is returned.

## Offline verification

```sh
python3 -m unittest scripts/migration/install_target_control_test.py
python3 -m py_compile scripts/migration/install_target_control.py scripts/migration/install_target_control_test.py
```

Tests use fake host, Docker and reviewed-module adapters. They cover strict
input and public-key identity, read-only effective SSH policy checks, exact
forced-key generation, preservation and concurrency of existing root keys,
private permissions, persistent owner and lost-response replay, active-ledger
refusal and concurrent ledger changes, actual resource adoption, source Redis
lineage, image identity, unit-override refusal and a fixed recovery-only
service command. Offline tests do not prove remote SSH authentication or host
readiness; those are separate live preflight checks owned by the parent.
