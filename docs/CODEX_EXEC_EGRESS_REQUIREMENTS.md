# Codex exec 统一出站需求

状态：2026-11-17，用户已确认全部决策及整体理解，grilling 完成；实现与验收已完成，见 [验收记录](CODEX_EXEC_EGRESS_VALIDATION_20261117.md)。Q12 经用户纠正为固定版本目标。实施基线：`9f97758e95fdb3bce5ceec587e06ee8d594cc729`。

## 已确认的需求

1. 入站可以是任意 agent harness，通过 Sub2API 支持的接口提交请求。是否采用 Codex exec 出站规则，不能依赖入站 User-Agent 是否属于 Codex 客户端。
2. 对齐的是模型推理请求的出站协议。调用方自己的系统提示词、对话历史、工具定义和工具结果须保留其含义；不替换为官方 Codex 的整套提示词或工具体系。
3. 出站客户端身份和版本由 Sub2API 服务端统一决定；Q14–Q15 最终将验收基准与实际出站共同固定为官方 `codex exec 0.158.0`。入站客户端版本、账号自定义身份与后台版本自动同步不得改变目标通道的版本。此决定覆盖 Q2 最初保留版本自动同步生效的安排；将来的版本升级不在本次范围内。
4. 上游范围为整个 ChatGPT/Codex 账号通道，包括 OAuth、PAT 及使用同一上游协议的账号；直连 OpenAI API 和第三方兼容上游不纳入此次修改。
5. 本次覆盖普通 HTTP 入站的 Responses、Chat Completions、Messages、透传和 compact。整个 WebSocket 入站链路均排除，包括 WS 转 HTTP 桥接。
6. 目标通道中新需求优先：去掉自动内容注入，旧的强制提示词模板、自定义客户端身份和关闭身份统一等机制不得绕过内容保留与统一出站身份。其他上游继续遵循各自规则。
7. 普通 Responses / Lite 布局根据最终账号、最终模型的已知服务端能力自动选择。能力未知时沿用请求声明的模式，未声明则使用普通模式；结构化日志明确记录“对齐未验证”，不得把此回退当作已经验证的对齐。
8. Q8、Q16：HTTP 协议和传输指纹一并验收，以官方 `codex exec 0.158.0` 的 Linux x86_64 发行包和固定 Linux 运行环境建立统一基准。入站 harness 的操作系统不改变这个出口；现有 arm64 正文样本仅作为历史回归。
9. Q9：目标 Codex HTTP 通道停止按入站 UA 或 `codex_cli_only` 判断客户端是否可用；正常 API key 鉴权、额度及分组权限继续保留。
10. Q10：仅允许保持原意的角色、字段、工具布局和关联 ID 转换；无法无损表达时明确返回不兼容错误。不静默删除/截短任务内容，也不从历史自行补上调用方未声明的工具。
11. Q11：未验证状态记录在后台结构化日志即可；此次不新增管理界面或调用方可见标记。
12. Q13：压缩验收要求方式、格式特征与解压后的正文一致，不要求相同输入产生逐字节相同的压缩输出。HTTP 头顺序、TLS 指纹分别对照固定官方基准；必要的随机值及会话隔离值核对格式和关联关系。
13. Q17：目标通道强制遵守固定传输规则。旧 TLS 关闭开关、自定义 profile 和插件不得绕过；可以保持目标指纹的代理/插件继续支持，确认无法保持时明确报配置不兼容，不静默回退为另一套传输。Q7 的模型能力未知兼容回退仍然成立，两者不混用。
14. Q18：接受来源明确的分层验收；官方原生直连 TLS 指纹单独采集，HTTP 头序、正文和压缩另行采集，各自记录来源与局限。解密代理的 TLS 不作为官方 TLS 证据，分开的采集不宣称为同一次完整原生直连抓包。
15. Q19：真实上游测试覆盖实际可用的账号类型；其他认证类型完成自动化测试并明确列为尚未实测。功能范围仍覆盖 OAuth、PAT、SetupToken，不因缺某种真实凭据扩大或缩减功能需求。
16. Q20：对于固定 Codex 协议无法兑现的回复长度、随机程度、停止标记等生成控制设置，忽略该设置，继续处理任务，并在后台日志说明未生效的参数。此例外仅针对这类生成控制，不允许据此删改任务指令、历史、工具定义或结果。
17. Q20 补充：忽略客户端不支持的设置后，最终发送给 OpenAI 的报文仍按官方 `codex exec 0.158.0 / Linux x86_64` 的行为构造；字段的省略、默认值、布局、身份和传输均以固定基准为依据，不另造网关自有的报文默认规则。官方支持的控制设置继续按其约定处理。




## 实施前基线与需求的差距

- `nativeCodexHTTPPolicy` 以入站 HTTP 标记、已识别 Codex User-Agent 和非 Messages bridge 为条件，限制了 reasoning、内部元数据、工具关联和 Lite 布局规则的适用范围。
- Chat Completions、Messages 和 WebSocket 转 HTTP 有独立的转换步骤，必须逐条验证最终出站行为。
- 有效原生 codex exec 请求目前保留其入站身份，违背统一由服务端决定的要求。
- 部分路径具有提示词注入或显式覆盖能力，需要确定它们与任务内容保留要求的优先级。

## 执行与验收

- 请求范围根据上游协议及 HTTP 入站路径判断，不根据 User-Agent、originator 或某个 harness 的名称判断。
- 在各入口的早期转换中保留有效 reasoning、内部元数据、工具调用与结果的关联，避免到最终出站时数据已被删除。
- 共享 HTTP 出站处理统一身份、最终模式与工具/指令布局；compact 入站适配为固定官方版本的 V2 压缩请求，再还原客户端响应。
- 入站请求对象不因某个账号的模式选择而被改写，避免重试或账号切换沿用上一账号的决定。
- 服务端能力复用现有账号模型元数据与已有明确的模型能力默认值；此次不新增推理热路径中的模型目录网络探测。
- 新测试从完整转发入口检查最终请求，覆盖任意/缺失 UA、与服务端不同版本的原生 exec、两种正文模式、工具续轮及配置冲突。
- Chat Completions 与 Messages 用调用方自己的系统提示和工具验证语义保留，明确检查自动追加提示与强制模板不再生效。
- APIKey / 第三方上游、真正 WS 和 WS 转 HTTP 桥接作为范围外回归，避免共享代码扩大变更。
- 普通/Lite 模式回退记录包含最终模型、选择来源与未验证状态，不记录提示词、工具参数或鉴权信息。

## 整体理解（用户已确认）

任意 agent harness 经普通 HTTP 接口调用 Sub2API 的 Codex 账号通道时，上游看到的是固定官方 `codex exec 0.158.0 / Linux x86_64` 的身份、HTTP 约定和传输特征，模型处理的仍是原 agent 的任务内容与工具语义。

- 固定基准同时约束验收和实际出站；后台自动版本同步、入站身份及旧传输覆盖设置不能改变它。
- 普通/Lite 模式按最终账号/模型能力选择；能力未知时兼容转发、日志标记未验证。已知传输不兼容时明确失败。
- 不再以 Codex 客户端身份准入；正常鉴权、额度和分组权限继续保留。任务内容/工具只作无损转换，否则明确失败。
- HTTP 头序、正文、压缩格式和原生 TLS 特征分层验收并记录证据来源；不要求压缩字节相同，不把分层证据伪称同一次直连抓包。
- OAuth、PAT、SetupToken 均实现支持；真实测试使用实际可用类型，其余完成自动测试并明确标为尚未实测。
- 整个 WS 入站链路、直连 OpenAI API Key 和第三方上游不属于本次范围。部署仍是后续工作，本次不自动更新线上服务。
- Codex 不支持的生成控制设置可忽略并记日志；最终报文仍严格按固定官方基准构造，不把这种兼容例外扩大到任务内容和工具。

## 生成控制参数事实核对

现有 Codex 转换会清理 `max_output_tokens`、`temperature`、`top_p` 等字段；Chat 的 `max_tokens`/`max_completion_tokens` 和 Messages 的 `max_tokens` 会先转换为随后被清理的上限字段。Chat 的 `stop`、Messages 的 `stop_sequences` 还会在接口转换时丢失，未发现独立的等价执行路径。Q20 已允许不支持的生成控制被忽略并记录；应在原始入口仍可识别参数时记录，并保证最终请求符合固定官方基准，不能依赖多级转换静默丢字段。

## 固定版本的 compact 事实

进一步源码及未修改官方二进制实测确认：0.158.0 已移除旧 compact dispatch，关闭 remote_compaction_v2 的配置不会生效。为同时满足“覆盖 compact 入站”和“固定官方出站”，实现采用 V2 协议适配，未发明不存在的旧端点指纹。参考 `testdata/codex_exec_0158_linux_amd64/legacy-compact-check/`。
